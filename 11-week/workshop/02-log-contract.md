# CP2 — Structured Log Contract

## 1. Purpose

This document defines a structured logging contract for Futbolix. Its purpose is to make application logs consistent, searchable, and useful when investigating failures across distributed services.

Futbolix includes an API Gateway, Reservation Service, Payment Service, RabbitMQ, PostgreSQL, and Wompi Sandbox in the reservation and payment journey. A common log format helps developers identify where an operation failed and correlate related events.

The examples in this document are illustrative. They describe the proposed logging contract and are not evidence that these logs have already been generated by the running application.

## 2. Required Log Fields

Every application log entry should be a valid JSON object containing these fields:

| Field | Description |
|---|---|
| `timestamp` | Date and time in ISO 8601 UTC format. |
| `level` | Severity level: `DEBUG`, `INFO`, `WARN`, or `ERROR`. |
| `service` | Name of the service generating the log. |
| `version` | Application version or build identifier. |
| `environment` | Deployment environment, such as `dev`, `qa`, or `main`. |
| `trace_id` | Identifier used to connect operations within the same distributed trace. |
| `span_id` | Identifier of the current operation within the trace. |
| `correlation_id` | Identifier used to correlate related operations across components. |
| `event` | Stable event name that can be searched. |
| `message` | Short, human-readable description of the event. |
| `duration_ms` | Operation duration in milliseconds, or `null` when not applicable. |

## 3. Domain-Specific Fields

The following optional fields provide additional business context:

- `reservation_id`: identifies the reservation involved.
- `court_id`: identifies the court involved.
- `reservation_status`: current reservation status.
- `payment_id`: identifies the payment operation.
- `payment_status`: current payment status.
- `dependency`: identifies a downstream dependency, such as Wompi Sandbox.
- `error_code`: stable code identifying a failure.
- `http_status`: HTTP response status when applicable.

Only fields relevant to the event should be included. Logs must not expose unnecessary personal or confidential information.

## 5. Severity Policy
Level	Purpose	Futbolix example
DEBUG	Detailed diagnostic information, mainly for development and troubleshooting.	Safe internal validation details.
INFO	Normal events showing application progress.	A reservation is created successfully.
WARN	Recoverable conditions or business outcomes that require attention.	A payment is rejected by a business rule.
ERROR	Technical failures that prevent an operation from completing as expected.	Wompi Sandbox times out during checkout.
Expected business rejections should not automatically be classified as technical errors. The severity must reflect the operational impact and the team's logging and alerting policies.
## 6. Sensitive Data and Masking Rules
Application logs must never contain:
- Passwords, JWTs, refresh tokens, or authorization headers.
- Payment card numbers, card security codes, or payment credentials.
- Secret keys, database credentials, or Wompi API secrets.
- Unnecessary customer personal information.
- Complete request bodies when they may contain sensitive data.
The implementation should allowlist safe fields, mask sensitive values when retention is necessary, and ensure that exception logs do not expose credentials or secrets.
## 7. Trace and Correlation Rules
- Related operations should preserve the same trace_id when trace context is available.
- Each operation should have its own span_id.
- The correlation_id should remain consistent across related operations when propagated by the application.
- Trace context should be propagated through HTTP requests and RabbitMQ message headers when supported by the implementation.
- Missing or invalid incoming trace context must be handled safely.
- Logs should remain useful even if trace propagation fails.
## 8. Acceptance Criteria
The logging contract will be considered implemented when:
1. Application logs follow the required JSON structure.
2. Required fields are populated consistently, with null used only where explicitly allowed.
3. Related operations can be searched using trace_id and correlation_id.
4. Technical failures can be distinguished from business rejections.
5. Sensitive information is excluded or appropriately masked.
6. Automated tests validate the required fields and trace-context propagation.
7. Example logs are clearly distinguished from logs captured during a real execution.
## 9. Checkpoint Outcome
This contract defines a common logging format for investigating the reservation and payment journey in Futbolix. The next step is to implement the required instrumentation in an actual service and verify its behavior through automated tests.
